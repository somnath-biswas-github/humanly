# Self-hosting

## Environment variables

| Variable | Required | Purpose |
| --- | --- | --- |
| `HUMANLY_API_KEY` | Yes | Authenticates every `/v1` request |
| `POSTGRES_PASSWORD` | Recommended | Changes the Compose database password |
| `HUMANLY_PORT` | No | Host port; defaults to 5000 |
| `HUMANLY_ALLOW_PRIVATE_CONNECTORS` | No | Allows private targets only for deliberate local testing |
| `DATABASE_URL` | Manual installs | PostgreSQL connection outside Compose |
| `PORT` | No | Container/server port; defaults to 5000 |

Keep `HUMANLY_ALLOW_PRIVATE_CONNECTORS=false` for a network-reachable
deployment. Add outbound firewall rules as an additional control.

## Startup and migrations

`docker compose up --build` starts PostgreSQL and the Humanly service. The
service retries database readiness and applies migration files from
`migrations/` before accepting traffic.

To run migrations manually:

```bash
npm ci
npm run migrate
```

## Health

`GET /health` checks PostgreSQL and returns:

- HTTP 200 and `ready: true` when the service is ready
- HTTP 503 and `ready: false` when PostgreSQL is unavailable

The Docker image and Compose service use this endpoint for health checks.

## Persistence

Compose stores PostgreSQL data in the `postgres_data` named volume and reserves
an `uploads` volume for future file-backed artifacts.

## Upgrade

Back up PostgreSQL first, then:

```bash
git pull
docker compose build
docker compose up -d
docker compose logs app
curl http://localhost:5000/health
```

Review [CHANGELOG.md](../CHANGELOG.md) for breaking changes before upgrading.
